## Architecture

```
ConfigProvider           ← existing
  └── App                ← NEW (provides App.useApp() context)
       ├── AntdAppRefBridge   ← NEW (renders null; copies App.useApp() into module ref)
       └── existing children
```

**Two consumption modes:**

| Caller type                                         | API                                                                                     |
| --------------------------------------------------- | --------------------------------------------------------------------------------------- |
| React components                                    | `const { message, modal, notification } = App.useApp()` — official antd hook            |
| Non-component (interceptors, store thunks, modules) | `import { antdApp } from '@/shared/lib/antd-app-ref'` then `antdApp.message.error(...)` |

The `antdApp` proxy falls back to antd's static API when the bridge hasn't mounted yet (initial boot frame). Calls always succeed; theme integration kicks in once bridge mounts.

## 1. `src/shared/lib/antd-app-ref.ts` (new file)

```typescript
import {
  App,
  message as staticMessage,
  Modal as staticModal,
  notification as staticNotification,
} from 'antd'
import { useEffect, type ReactNode } from 'react'

/**
 * Bridges antd `<App>` instance methods (message/modal/notification) to a
 * module-level ref so non-component code (interceptors, store thunks, util
 * modules) can use them with ConfigProvider context applied (theme tokens,
 * style providers, etc.).
 *
 * Mode of operation:
 *  - `AntdAppRefBridge` mounts once inside `<App>` (see providers.tsx). It
 *    calls `App.useApp()` and writes the bound instance methods to `_ref`.
 *  - Non-component callers import `antdApp` and use its proxy properties.
 *  - Before the bridge mounts (one frame during initial boot), the proxy
 *    falls back to antd's static API. Calls still work, just without
 *    ConfigProvider context for that brief moment.
 *
 * Why a getter-based proxy instead of a plain object:
 *  - Bridge sets `_ref` AFTER first render → cached reference at module load
 *    would point at static API forever. Getters re-read `_ref` per call.
 *
 * React components should prefer `App.useApp()` directly — it's the official
 * API and re-renders correctly. Use `antdApp` only when no component context
 * is available.
 */

type AppInstance = ReturnType<typeof App.useApp>

let _ref: AppInstance | null = null

export const antdApp = {
  get message() {
    return _ref?.message ?? staticMessage
  },
  get modal() {
    return _ref?.modal ?? staticModal
  },
  get notification() {
    return _ref?.notification ?? staticNotification
  },
}

/** Mount ONCE inside `<App>`. Renders null. */
export function AntdAppRefBridge(): ReactNode {
  const app = App.useApp()
  useEffect(() => {
    _ref = app
    return () => {
      // Only clear if this effect's value is still the active ref. Defensive:
      // if React strict-mode runs effect twice, second cleanup shouldn't wipe
      // a freshly-set ref from the second mount.
      if (_ref === app) _ref = null
    }
  }, [app])
  return null
}
```

## Notes on subtle points

### Why `<App>` inside `<ConfigProvider>` and not the other way

antd's `<App>` reads theme tokens from `<ConfigProvider>` to style its message/notification toasts. Inverting the order would yield un-themed toasts. The order in providers.tsx is `ConfigProvider > App > children` — same as antd's recommended setup.

### Why a bridge component instead of `App.useApp()` directly in `AntdThemeBridge`

`AntdThemeBridge` doesn't have `<App>` as ancestor at its own render (it renders `<App>` as descendant). `App.useApp()` only works for descendants of `<App>`. A separate bridge component lives inside `<App>` and can call the hook.

### Why dev warnings should disappear

After T2.0a, no code imports `message`/`Modal`/`notification` as static API. The static API only triggers warnings when called; `antdApp` proxy routes through bridged instance methods → no warnings.

Caveat: during initial boot frame (before bridge mounts), `antdApp` falls back to static methods. If an interceptor fires _during_ boot (e.g., the bootstrapAuth call hits a 401), the static fallback may trigger one warning. Acceptable — rare race, not a regression.

### When does the bridge unmount

Only when `<App>` unmounts. That happens when `<ConfigProvider>` re-mounts (theme algorithm changes between light↔dark trigger this in some antd versions). Cleanup nulls the ref; React immediately re-renders the bridge with the new `<App>` and sets ref again. Static fallback covers the gap of 1 frame.

### `App.useApp()` return shape

Returns `{ message, modal, notification }` where each is a hook-bound instance. Methods: `message.success/error/warning/info/loading`, `modal.confirm/warning/error/info/success`, `notification.open/success/error/etc`. Same surface as the static counterparts, so the migration is mechanical.

### Components: prefer hook or proxy

For consistency in Task 2 onward, **components should use `App.useApp()`** directly:

```tsx
import { App, Button } from 'antd'

function DeleteButton({ onConfirm }) {
  const { modal } = App.useApp()
  return (
    <Button danger onClick={() => modal.confirm({ ... })}>Delete</Button>
  )
}
```

`antdApp` proxy is reserved for non-component contexts. Will codify in skill template T2.5.
