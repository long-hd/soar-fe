## Mission + DoD

**Mission**: Ship a fully-functional `system/user` CRUD page that exercises every piece of foundation (A0–A5 + AA + T2.0a + T2.0b) and serves as the template all subsequent CRUD pages (role, dept, dict, menu, post) will be copy-modified from.

**Definition of Done**:

- [ ] Sider menu "User Management" → opens tab → list page renders
- [ ] Search form: 5 fields (username, mobile, status, deptId, createTime range) — submit + reset
- [ ] Table: 7 columns (username, nickname, deptName, mobile, status with Switch toggle, createTime, actions) + bulk-delete checkbox column
- [ ] Pagination + sort (username ASC/DESC, createTime ASC/DESC)
- [ ] Create user modal — full form, password required
- [ ] Edit user modal — same form, password field hidden
- [ ] Delete single + delete-list (bulk) with `Modal.confirm`
- [ ] Reset-password modal
- [ ] Update-status inline Switch (no confirm modal — per Q T2.0.3 prior)
- [ ] All actions permission-gated via `<HasPermission>` + `usePermission`
- [ ] All `<DictSelect>` (status, sex), `<DeptTreeSelect>` (deptId), `<PostSelect mode="multiple">` (postIds) wired
- [ ] All toasts via `App.useApp().message` (no static API)
- [ ] All strings via i18n keys (no hardcoded EN)
- [ ] `skills/crud-page.md` updated to snapshot reality at T2.5

**Not in Task 2 scope** (defer):

- Role assignment (separate BE endpoint, separate UX, Phase 5C)
- Excel export / import (BE has it, Phase 5C polish per KICKOFF)
- Detail page (not needed yet; `parentTabKey` (#13) deferred)

UI permission gates (5 codes):

- `system:user:query` — view list (gate at menu level, not action level — BE menu filter already does this)
- `system:user:create` — Create button in toolbar
- `system:user:update` — Edit button + Switch toggle
- `system:user:update-password` — Reset Password button
- `system:user:delete` — Delete button + bulk-delete button

## DTO shapes (BE → FE TypeScript mapping)

Will codify in T2.1 `types.ts`. Sketch here for the decisions doc:

```typescript
// User table row + form edit fetch
interface UserRespDTO {
  id: number
  username: string
  nickname: string
  remark?: string
  deptId?: number
  deptName?: string // BE joins, no FE lookup needed
  postIds?: number[]
  email?: string
  mobile?: string
  sex?: number // 1=Male 2=Female 3=Unknown (dict user_sex)
  avatar?: string
  status: number // 0=Enabled 1=Disabled (dict common_status)
  loginIp?: string
  loginDate?: string // ISO Instant
  createTime: string // ISO Instant
}

// Create + Update (unified, BE checks isPasswordValid)
interface UserSaveReqDTO {
  id?: number // undefined = create, set = update
  username: string
  nickname: string
  remark?: string
  deptId?: number
  postIds?: number[]
  email?: string
  mobile?: string
  sex?: number
  avatar?: string
  password?: string // required when id absent, ignored when id present
}

// Search filters
interface UserFilters extends Record<string, unknown> {
  username?: string
  mobile?: string
  status?: number
  deptId?: number
  createTime?: [string, string] // ISO Instant pair, length 2 — matches BE @Size(min=2,max=2)
}

// Side endpoints
interface UserUpdateStatusReqDTO {
  id: number
  status: number
}
interface UserUpdatePasswordReqDTO {
  id: number
  password: string
}
```

## Risks + open items

1. **#13 parentTabKey deferred**: User detail page not in Task 2 scope. When first detail page lands (Phase 5C?), parentTabKey BE migration + FE consume = block T3.
2. **Self-protection FE-only**: T2.0-D8 enforces in UI, BE service also enforces. If FE check missed, BE returns error — UX worse but not unsafe.
3. **Status Switch race condition**: User clicks Switch fast 2x → 2 in-flight requests. Mitigation: disable Switch during request, re-enable on settle. Will document in T2.4.
4. **Bulk delete performance**: BE `/delete-list` accepts unbounded `ids[]`. UI doesn't cap selection. If user selects 1000 rows → request size large. Acceptable for now; cap later if observed.
5. **Form validation rules**: BE returns 200 + `code !== 0` for biz validation (e.g., duplicate username). error-interceptor shows toast. Form modal doesn't need its own validation feedback. May result in user typing → submit → toast appearing far from input → UX friction. Phase 5C polish: per-field error mapping.
